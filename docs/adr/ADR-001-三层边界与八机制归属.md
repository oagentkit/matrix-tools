# ADR-001 · 三层边界与八机制归属

| 项 | 内容 |
|---|---|
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-11-28 |
| **背景** | oagentkit 演进评审 2.3-问题一：Agent / Runtime / Kernel 三层**都去实现**生命周期、超时、重试、失败分类、状态、任务调度、事件、恢复时，就会出现多套相似机制——而归属此前只存在于各处 ADR 的散文里，**没有判定**。issue `matrix-tools#255`。 |
| **决策** | ① 三层职责按下表划界（判定归属，不是代码目录）；② 八机制的**判据单源**落 `modules.json` 的 `mechanisms` 字段（机读），`gen_llms_txt.py` 渲染成对外文档，`verify_mechanism_ownership.py` 判红；③ `runtime` / `goagent-runtime` 短名撞车选**消歧字段**（`qualifier`），不改名。 |
| **后果** | 新增机制包若不在归属表登记 ⇒ CI 红；llms.txt 的两个 runtime 仓带消歧限定词；改名路径被否决（理由见 §三），将来若要改名须另开 ADR 推翻本单；「新增机制包无归属 ⇒ 判红」从 review 口号变成 `drift` job 的红灯。 |
| **依据** | 四仓 `go.mod` 实况（2026-11-27/28 核对，见 §一）；kernel `ADR-0003`（与上游矩阵的分层）、`ADR-0009`（调度判据归属）、`ADR-0001`（领域知识红线）、`docs/OAGENTKIT-OVERLAP.md`；各机制包的 import 实测（2026-11-28，逐包 grep）。 |

> **一句话结论**：三层各管一类问题、八机制各有唯一判据单源——归属写进
> `modules.json` 并由门禁守着，而不是散在文档里靠人记。

## 一、三层职责（判定归属，不是代码目录）

| 层 | 职责 | 仓 | **不做什么** |
|---|---|---|---|
| **Agent**（思想层） | 智能行为与决策编排：路由、黑板、派发守卫、澄清、反思 | `oagentkit/agent`（tier3） | 不定义任务状态词表、不做确定性调度判据 |
| **Runtime**（运行时层） | 执行环境与运行时装配：进程机制件（pacer / procx / hookx）与应用装配（会话、集群、agentloop） | `oagentkit/runtime`（tier0）、`yi-nology/goagent-runtime`（tier5） | 不写判据——判据来自 Kernel，装配层只接线 |
| **Kernel**（机制层） | 可验证的确定性机制：状态词表、调度判据、断点恢复、失败分类 | `yi-nology/goagent-kernel`（tier4） | 不认识领域概念（`ADR-0001` 领域知识红线）、不做模型调用与工具实现 |

三层是**判定归属**，不是「代码只能放这里」：装配层可以消费机制件，但不能
另写一份相似判定。判词沿用 kernel 侧定调——**Agent Execution Kernel，不是
Agent Framework**（kernel#528：专家角色 / Prompt / 工具实现 / 领域判断全属宿主）。

### 依赖边实况（`go.mod`，2026-11-27/28 核对）

| 模块 | 第一方依赖 | 说明 |
|---|---|---|
| `oagentkit/agent` | `llm`、`textx` | 思想层**零依赖 kernel**——上下游判断成立，保持 |
| `oagentkit/llm` | `textx` | 同上 |
| `oagentkit/textx` | （无） | tier0 纯函数 |
| `oagentkit/toolgate` | `mcpkit`、`guardx` | 审批裁决组合上游安全件 |
| `yi-nology/goagent-kernel` | `guardx`、`runtime`、`toolgate`、`toolname`（`mcpkit` indirect） | kernel v0.80.0 **只取机制件**，不取思想层 |
| `yi-nology/goagent-runtime` | `agent`、`goagent-kernel`、`guardx` | 菱形装配：思想层 + 机制层同时伸手 |

### 越级边白名单

装配层伸手两层是**有意的边**，但必须显式声明而不是顺手 import：

- `goagent-runtime` → `oagentkit/agent/roundguard`（4 处：`cluster` / `runtime` 两文件 / `agentloop`）——装配层要接**回合预算与收口策略**，那是思想层的机制件；
- `goagent-runtime` → `guardx` 直连（sandbox / invoke）——装配层要接**安全围栏**。

两条都已登记在 `goagent-runtime` 的 `dependsOn`，`verify_import_direction.py`
对账「声明 ↔ 真实 import」：**未声明的边判红**。反向红线（思想层零依赖 kernel）
同样由它守。新增越级边的顺序是**先改 `dependsOn` 再改代码**。

## 二、八机制归属表（机读单源：`modules.json` `mechanisms`）

下表是叙述版；**机读单源是 `modules.json` 的 `mechanisms` 字段**，本表与它
冲突时以字段为准（字段由 `verify_mechanism_ownership.py` 校验：引用的包/仓
必须真实存在）。「消费方」为 2026-11-28 的 import grep 实测快照（矩阵内、
排除包所属仓自身）；import 对账的机器面在 `verify_import_direction.py`，
本表不重复那份判定。

| 机制 | 判据单源（owners） | 同族包（claims） | 消费方 | 关键词 |
|---|---|---|---|---|
| **生命周期** | `goagent-kernel/contract` — 任务/会话状态词表与终态判定（`AllStatuses` / `ClassifyStatus`） | — | goagent-runtime | `lifecycle` |
| **超时** | `goagent-kernel/deadline` — 会话墙钟错误身份；`guardx/toolfail` — 超时归类与重发语义 | — | goagent-kernel、toolgate | `timeout` `deadline` |
| **重试** | `guardx/toolfail` — 可重试性判定（`ClassUnknown` 不可重试） | `goagent-kernel/retryplan` | goagent-kernel、toolgate | `retry` |
| **失败分类** | `guardx/toolfail` — 调用失败分类学；`mcpkit/iface` — MCP 协议层 `ErrorKind` | — | goagent-kernel、toolgate | `toolfail` `failclass` |
| **状态** | `goagent-kernel/statemachine` — 环节状态枚举与谓词（词表值别名 contract，#354/#357） | —（`promptx/filestate` 词面命中但属 promptx 域，`exempt` 带理由） | —（矩阵内零 import，enum 出口是宿主面） | `state` `statemachine` |
| **任务调度** | `agent/dispatch` — 能不能派（可达性/深度/自派发）；`goagent-kernel/scheduling` — 按什么次序（优先级/公平/配额/背压）；`toolgate/toolsched` — 同时跑几个；`goagent-kernel/dispatch` — 失败后还能不能再派 | — | goagent-runtime | `sched` `dispatch` |
| **事件** | `goagent-kernel/eventbus` — 任务事件词表（机制层 snake_case 单源）；`runtime/hookx` — 泛型钩子传输；`runtime/notifyx` — 泛型通知传输；`runtime/progress` — 泛型有损广播 | `runtime/notifyx/hook`、`goagent-kernel/hookengine` | goagent-runtime、goagent-kernel | `event` `hook` `notify` `progress` |
| **恢复** | `goagent-kernel/checkpoint` — 断点与续跑（Snapshot/Resume） | `goagent-kernel/reconcile`、`goagent-kernel/finalize`、`goagent-kernel/ownership`、`goagent-kernel/drain`、`goagent-kernel/watchdog` | goagent-runtime | `checkpoint` `reconcile` `resume` `recover` `drain` `finalize` `ownership` `watchdog` |

几条**容易被写成第二份实现**的边界，在这里钉死：

- **调度四判据面分立**是 kernel `ADR-0009` 的已裁结论（可达性归 `dispatch`
  门面、次序配额归 `scheduling`），本表引用不重开；kernel 原可达性门面
  v0.35.0 已整包删除，消费方直连上游 `agent/dispatch`。
- **超时三轴**（会话墙钟 / 模型 / 工具）实现分立，但「超时算哪类、能否重发」
  的**判据**单源是 `guardx/toolfail`——三轴对照表由 `guardx#222` 交付。
- **事件词表分层单源**：机制层 `kernel/eventbus`（snake_case ~40 事件）+
  应用层 `goagent-runtime` `run_*` / `worker_*`（runtime#42 裁决）；
  `runtime/progress` 是泛型有损广播，与任务事件语义不同，不要混用。
- **恢复面**与 kernel#527 的三平面是**正交分类**：#527 按 kernel 仓内平面切
  （checkpoint 划执行面写入侧），本表按跨仓机制族切（写入与读取同属
  断点续跑链路）——两套分类各管各的，不互相改写。

## 三、`runtime` / `goagent-runtime` 短名撞车：三选一裁决

「runtime」一名双占：`oagentkit/runtime`（tier0 进程运行时机制件，kernel
依赖它）与 `yi-nology/goagent-runtime`（tier5 应用运行时装配层）。评审要求
三选一：

| 选项 | 裁决 | 理由 |
|---|---|---|
| **A. 改名** | ❌ 否决 | 两个都是**已发布 module**（kernel `v0.80.0` require `oagentkit/runtime`；`goagent-runtime` 刚发 `v0.8.0`）。改 module path = 跨 org breaking：全部历史 tag、下游 require、站点文档、llms.txt、迁移指南一起改。工具链里已有的改名先例（kernel `toolgate` → `tooldisclose`）是**仓内包级**改名，成本低一个量级，不能类比到 module 级。 |
| **B. 只在文档里强区分** | ❌ 否决为独立方案 | 会漂——本仓的存在理由就是「文档承诺没有机器校验」。可以作为 C 的**渲染产物**保留，但不能是唯一手段。 |
| **C. `modules.json` 消歧字段 + 生成链渲染** | ✅ 采纳 | 新增 `qualifier` 字段（两个仓都写），`gen_llms_txt.py` 渲染成模块条目下的「消歧」行；import 路径本就全限定（`runtime/hookx` vs `goagent-runtime/agentloop`），编译面无冲突，撞的只是**短名引用**。字段机读、生成确定、可被门禁守。 |

**防复发**：`verify_mechanism_ownership.py` 对「一个仓名是另一个的后缀」的
仓对强制双方都带非空 `qualifier`——将来再出现 `xxx` / `fooxxx` 撞名时，
不写消歧字段就红，而不是等文档再漂一轮。

## 四、门禁（归属怎么被守住）

按本仓 AGENTS 的硬规则，新增守卫的顺序是「登记 → 判据脚本 → CI →
`verify_inventory` 通过」：

1. `scripts/invariants.json` 登记 `mechanism-ownership`（oracle independent：
   只读 `modules.json`，不 import 任何生成器）；
2. `scripts/verify_mechanism_ownership.py`：表自洽 + 关键词网 + 撞名消歧，
   `--selftest` 带反证样本（无归属包 / 陈旧引用 / 删机制 / 空 keywords /
   exempt 无 reason / 撞名缺 qualifier，每种形态一条断言）；
3. `.github/workflows/matrix-tools-ci.yml` 的 `drift` job 接真判定步骤，
   自测由 `selftest_all --shard` 按 AST 自动发现；
4. `verify_inventory.py` 通过（真判定 + 自测接线两腿都在）。

**关键词网的诚实边界**：关键词按**包名**匹配——抓「名字长得像机制」的包，
抓不住名字不带词的语义重复（那是 review 的活）。漏报靠关键词维护，误报靠
`exempt` 带理由豁免。判据只在 `modules.json` 自身上做，不需要克隆矩阵
（克隆面归 `matrix-local-guards`）。

## 六、派发与调度判据归属表（agent#177 附录）

评审 2.3-问题四（多 Agent 防过度抽象——「确定性的调度判据应有明确归属」）的
落地面。§二「任务调度」机制行是四判据面的粗粒度声明；本表细化到**判据级**
（谁可以调谁 / 递归派发怎么限 / 并发怎么排 / 预算怎么卡 / 上下文谁可见 /
任务冲突谁裁 / 失败后往哪走），并给「决策层（Agent 提供）」与「禁止落点」
两列——判据是机制（确定性、可判红），决策是智能（Agent/宿主）。

### 归属表

| 判据 | 唯一归属 | 决策层（Agent/宿主提供） | 禁止落点 |
|---|---|---|---|
| 可达性（谁可以调谁） | `agent/dispatch.Guard`（allow 矩阵 + 自派发拒绝） | 拓扑边（EdgeSource）由宿主装配；Agent 决定要不要派 | kernel / runtime / toolgate 不得另写可达性判定 |
| 递归上限（派多深） | `agent/dispatch.Guard` `maxDepth`/`AssertDepth` | 上限是宿主显式配置（漏配 fail-fast，agent#89） | kernel delegate **不设**深度判定（有意）；`kernel/scheduling.MaxQueue` 是**队列深度**（背压轴）——同词异义不许并（见下） |
| 并发调度（同时跑几个） | `toolgate/toolsched`（优先级三层 + 注解驱动 + 调用限流） | Agent 不定并发数（那是资源判定） | kernel **无对应物且不该有**（调度判据归属 kernel ADR-0009：属 agent 运行时，不属编排内核） |
| 优先级/公平/配额/背压（怎么排） | `kernel/scheduling`（纯函数判定面） | Agent 提供优先级输入/权重 | toolgate / agent 不得另写次序判定 |
| 执行级预算（调用前判定） | `llm` 任务级预算面（budgetGate：判定必须在调用前，事后扣减判不合规——llm#241 conformance 钉） | Agent 决定花多少（预算数额是决策） | `textx/budget` 是**上下文窗口预算**（同词异义，exempt 记档）；回合级预算在 `agent/roundguard`（回合守卫轴，不同判据面） |
| 上下文可见性（谁看得见什么） | `agent/blackboard`（黑板可见域）；`promptx` 是跨会话注入面（消费方） | Agent 决定共享什么 | 其他层不设可见性判定 |
| 任务冲突裁决 / 失败恢复路由 | 冲突裁决：`kernel/scheduling`（配额/公平裁决面）；失败恢复路由：`kernel/dispatch`（改派失败面 failover） | Agent 决定降级策略与改派目标 | `agent/dispatch` 只管**能不能派**，不管失败后改派（判据正交，kernel ADR-0009） |

### 递归上限单源结论（issue「对齐或记有意分歧」的裁决）

**单源 = `agent/dispatch.Guard`，现状即对齐，无代码改动**。存量核查证据
（2026-11-28 逐仓 grep）：

- `kernel/delegate`（Offer/Route/Receipt）**零深度判定**——跨进程派发的深度
  在调用方守卫判定，delegate 只管协商（有意分工）；
- `kernel/dispatch`（改派失败面）包头明言「不碰 allow 矩阵、深度上限」；
- `kernel/scheduling/backpressure.go` 的 `MaxQueue` 是**等待队列深度**（背压
  裁决的输入），不是派发递归深度——**同词异义**，归属表按判据分列防误并
  （将来谁想把两者「对齐」成一个参数，先读本节）。

### 防过度抽象红线（落 `oagentkit/agent` AGENTS.md，agent#177）

多 Agent ≠ 多个 ReAct 循环。agent 层新增「多专家协作」能力时：确定性判据
（可达性/递归上限/并发/优先级/预算/可见性）**一律进上表既有归属面**，只有
决策内容（派谁、给多少预算、共享什么、失败降级到哪）留在宿主编排代码；
禁止在 agent 层新建第二份调度判定。

### 判据落点判红（机器面）

机读单源是 `modules.json` `mechanisms.scheduling.criteria`（五条判据 ×
keywords + repos）；`verify_mechanism_ownership.py` §2.5 判红：命中判据关键词
的包必须落在**命中判据的 repos 并集**内（登记了也红），同词异义走 `exempt`
带 reason（`textx/budget` 是登记样例）。自测 ⑨–⑫ 钉四种形态：落点越界 /
命中未登记 / exempt 记档放行 / 跨判据并集放行。
